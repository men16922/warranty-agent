# L4 — 검증: "실행됨 ≠ 나아졌음"

`Satisfies: REQ-201, REQ-202, REQ-203, REQ-204, REQ-205, REQ-206`

> **이 문서가 이 프로젝트의 논지다.**

---

## 1. 문제 진술

대부분의 remediation 에이전트는 조치를 실행하고 **성공을 보고한다.**
**실행 성공은 증상이 사라졌다는 뜻이 아니다.**

- 파드를 재시작했다 → 재시작은 성공했다 → **오류율은 그대로다**
- 스케일을 올렸다 → API가 200을 줬다 → **지연은 더 나빠졌다** (콜드 스타트)
- 트래픽을 옮겼다 → 옮겨졌다 → **원인이 다른 곳이었다**

세 경우 모두 **로그는 똑같이 초록이다.**

## 2. 절차

```
   ① baseline  = read(contract.health_signal)          ← 조치 전
   ② execute
   ③ wait VERIFY_DELAY
   ④ after     = read(contract.health_signal)          ← 같은 스펙, 같은 창
   ⑤ verdict   = judge(baseline, after, contract.recovery_criterion)
```

**④가 ①과 같은 함수를 타는 것이 핵심이다**(REQ-202). 두 곳에서 각자 질의를 만들면
언젠가 다른 걸 재고, **그 어긋남은 조용하다.**

## 3. 판정 — 세 갈래, 그리고 넷째

```
   명확히 만족       →  recovered
   명확히 위반       →  not_recovered
   tolerance 안쪽    →  ★ 모델에 위임 (REQ-204)
   신호를 못 읽음    →  unverifiable   (성공 아님, REQ-205)
```

### 3.1 ★ 모델이 판단하는 자리 (REQ-204)

**규칙으로 못 쓰는 판단이 실제로 있다:**

> 오류율은 60% 내렸다. 그런데 지연 p95는 올라갔다. 회복인가?

규칙으로 쓰면 임계값을 하나 더 만들고, 그 임계값이 또 애매한 경우를 만든다.
**모델은 이걸 문장으로 답할 수 있고, 그 문장이 근거로 남는다.**

```jsonc
"verification": {
  "verdict": "not_recovered",
  "decided_by": "model",
  "rationale": "Error rate improved 60% but p95 latency rose 2.3× above baseline;
                the action traded one symptom for another rather than resolving it.",
  "baseline": {...}, "after": {...}
}
```

⚠️ **이 자리가 없으면 이 시스템에서 LLM은 자연어를 도구 호출로 바꾸는 파서일 뿐이다.**
심사에서 *"에이전트가 뭘 하나"*라는 질문을 받는 자리가 정확히 여기다.

⚠️ **모델의 판단은 기록되지만 무제한이 아니다**: 모델은 `tolerance` 안쪽에서만 불린다.
명확한 경우까지 모델에 맡기면 판정이 비결정적이 되고 REQ-802가 깨진다.

### 3.2 `unverifiable`은 성공이 아니다 (REQ-205)

신호를 못 읽거나 계약이 없으면 `unverifiable`로 남기고 **사유를 적는다.**

⚠️ **조용한 성공이 이 프로젝트가 겨냥하는 실패 그 자체다.** 여기서 관대해지면 논지가 무너진다.

## 4. 타이밍 (REQ-206)

```python
VERIFY_WINDOW_S = 120   # 재측정 창
VERIFY_DELAY_S  = 135   # 조치가 반영되기까지 기다리는 시간 (= 창 + 15)
```

⚠️ **영상 길이에 맞춘 값이고, 상수 한 곳에 있다.** 타이머를 줄이는 것은 실증 최적화지만,
**결과를 하드코딩하면 실증이 아니다.**

⚠️ Cloud Monitoring은 지표 도착에 지연이 있다. `VERIFY_DELAY_S`가 너무 짧으면
**아직 안 온 데이터로 판정**하게 되고, 그건 `unverifiable`이 아니라 **거짓 판정**이다.
⇒ 재측정 창에 **데이터 포인트가 0개면 `unverifiable`**로 떨어뜨린다.

## 5. 검증이 실패하는 방식 (알고 있는 것)

| 실패 | 증상 | 처리 |
|---|---|---|
| 지표가 아직 안 옴 | 빈 창 | `unverifiable` (거짓 판정 금지) |
| 조치와 무관한 변동 | 회복으로 보이지만 우연 | ⚠️ **못 푼다.** §6 |
| 기준선 자체가 이상치 | 비교가 무의미 | 기준선 창을 조치 창보다 길게 |
| 계약의 기준이 틀림 | 검증이 일관되게 틀림 | 회복률은 *"우리 기준으로"*임을 명시 |

## 6. ⚠️ 알려진 한계 — 인과가 아니라 상관이다

**조치 후 신호가 회복됐다는 것이 조치가 원인이라는 뜻은 아니다.**
부하가 저절로 줄었을 수도 있다.

- 완화: 롤백 후 **다시 재측정**한다(REQ-304). 되돌렸는데도 좋으면 조치가 원인이 아니었다는
  증거가 된다 — **약한 자연 실험**이다.
- 그래도 인과는 못 세운다. **이 한계를 영상에서 말한다.**
