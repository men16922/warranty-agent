# L4 — 원자적 롤백 (GCP 전용인 이유의 절반)

`Satisfies: REQ-301, REQ-302, REQ-303, REQ-304, REQ-305`

---

## 1. 왜 이게 GCP 전용을 정당화하는가

자동 롤백은 **되돌림이 믿을 만할 때만** 안전하다. 그런데 되돌림의 성질은 클라우드마다 다르다:

| | 되돌림 |
|---|---|
| 일반적인 K8s 롤아웃 | **점진적**. 분 단위. 중간 상태가 존재한다 |
| **Cloud Run 리비전 트래픽 전환** | **원자적**. 즉시. 중간 상태가 없다. **그리고 배분을 다시 읽어 확인할 수 있다** |

**중립적인 에이전트는 앞줄에 맞춰야 한다** — 그래서 자동 롤백을 못 하거나, 하고도 못 믿는다.
`warranty`는 뒷줄에 올인한다.

## 2. 계획은 조치 **전에** 확보된다 (REQ-301)

```
   계약에서 rollback_plan.previous_revision 읽기   ← 조치 전
   원장 항목에 고정
   조치 실행
   (필요 시) 롤백 = 고정된 리비전으로 트래픽 100%
```

**롤백에 필요한 추가 API 호출은 0이다.**

⛔ **위 블록의 두 번째 줄(*"원장 항목에 고정"*)은 코드에 없는 단계다 — §7.**

⚠️ **조치 후에 롤백 대상을 찾으면, 바로 그 조치가 깨뜨린 상태에 의존하게 된다.**
조치가 리비전을 바꿨는데 "직전 리비전"을 조치 후에 물으면 **방금 만든 것**이 나온다.

## 3. ★ 롤백은 증명된다 (REQ-303)

```
   ① 트래픽 100% → previous_revision  (API 호출 1회)
   ② 서비스를 다시 읽어 실제 배분 확인
   ③ rollback.verified_traffic == {previous_revision: 100} 인가
```

⚠️ **"롤백했다"는 주장이고, "트래픽이 이전 리비전으로 갔다"는 측정이다.**
②를 빼면 API가 성공했는데 배분이 안 바뀐 경우를 못 잡는다.

## 4. ★ 롤백도 검증한다 (REQ-304)

롤백 후 **신호를 다시 잰다.**

```
   rollback.signal_restored = (재측정 신호가 baseline 수준으로 돌아왔는가)
```

| 결과 | 무슨 뜻인가 | 처리 |
|---|---|---|
| `true` | 조치가 문제를 만들었고, 되돌려서 해결됐다 | 정상 종료 |
| `false` | **되돌렸는데 안 돌아왔다** → 원인이 조치가 아니었다 | **에스컬레이션** |

⚠️ **`false`가 값진 결과다.** 이건 "우리가 엉뚱한 걸 고치고 있었다"는 정보이고,
그걸 **자동으로 알아내는 시스템은 드물다.** 그리고 이게 §2 검증의 인과 한계를 부분적으로
메우는 **약한 자연 실험**이다.

## 5. 되돌릴 수 없으면 (REQ-305)

계약이 비가역이라 선언했거나 롤백이 실패하면 **에스컬레이션하고 더 조치하지 않는다.**

⚠️ **실패한 자동화가 계속 시도하는 것이 가장 나쁜 상태다.** 한 번 더 해서 나아질 근거가
없다면 멈추는 것이 옳다.

## 6. 조치 카탈로그 제약 (요구사항 Q1과 이어진다)

`resource_label` 귀속이 성립하고 트래픽으로 되돌림이 증명되려면:

- 대상은 **Cloud Run 서비스**이고
- 조치는 **리비전/트래픽을 바꾸는 것**이며
- **한 조치 = 한 리소스**여야 한다

⇒ 데모 조치 2종을 이 제약 안에서 고른다. 밖의 조치는 계약을 `none`/비가역으로 선언하고
**자동 대상에서 빠진다** — 그것도 정상 동작이다.

## 7. 알려진 한계

- ⛔ **§2의 절차 블록에 코드에 없는 단계가 있다 — *"원장 항목에 고정"*.**
  코드(`usecases/remediate.py`)가 조치 **전에** 고정하는 것은 맞지만, 고정되는 자리는
  원장 항목이 아니라 **루프의 지역 이름**(`plan = contract.rollback_plan`)이다.
  `LedgerEntry`에는 조치 시점의 `previous_revision`을 실을 칸이 없다 — 롤백 대상은
  사후에 `Rollback.verified_traffic`의 키로만 남는다. ⇒ **되돌린 경우의 대상은
  원장이 말하지만, 되돌리지 않은 경우에 무엇으로 되돌릴 수 있었는지는 원장에 없다.**
  ⚠️ 그래서 **design 02§2와 달리 이 블록은 파싱하지 않는다**: 파싱하면 이 어긋남 때문에
  가드가 처음부터 red이고, 초록으로 만들려면 설계나 원장 스키마를 건드려야 한다
  (설계 변경은 사람 판단이라 범위 밖이다). 자리는 AST로 묻고, 어긋남은 여기 적어 둔다 —
  근거는 `docs/evidence/mutations.md`의 M-60 절이다.
- **계약은 루프 시작에 한 번 읽은 얼어붙은 값이다.** 그래서 *"계획을 조치 전에 읽는가"*는
  값으로는 증명되지 않는다 — `plan = ...`을 조치 뒤로 내려도 계획도 판정도 원장도
  안 바뀐다(M-60은 살아남았다). 그 자리를 지키는 것은 값이 아니라 **구문 검사**다.
