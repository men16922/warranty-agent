# L4 — 에이전트 런타임 (ADK · Gemini · Cloud Run)

`Satisfies: REQ-501, REQ-502, REQ-503, REQ-101`

---

## 1. 대회 필수 요건과의 대응

| 요건 | 우리의 충족 |
|---|---|
| Gemini 3.5 이상 (Gemini API 또는 Vertex AI) | **Vertex AI · Gemini 3.5 Flash** |
| Google Agent Framework 1개 이상 | **ADK** |
| Google Cloud 인프라 1개 이상 | **Cloud Run** (+ Firestore, BigQuery) |

⚠️ **Flash를 고른 이유는 비용이다.** 이 프로젝트는 자기 모델 비용을 원장에 적으므로
(REQ-503) **모델 선택이 데모에 그대로 보인다.** Pro를 쓰면 장부의 자기 비용 항목이
다른 모든 항목을 압도한다 — 그 자체가 흥미로운 발견이지만, 데모의 초점을 흐린다.

## 2. ⚠️ 이 문서에서 가장 중요한 경고

**ADK의 실제 API를 아직 확인하지 않았다.** 이 절의 구성은 *의도*이고, **T2에서 실물로
검증되기 전까지는 주장이 아니다.**

레퍼런스 저장소가 정확히 이 실패를 겪었다: Azure SDK의 어떤 클래스를 임포트하는 코드가
있었고 테스트는 통과했는데, **테스트가 그 모듈을 스텁하고 있었고 그 클래스는 실제
라이브러리에 존재하지 않았다.** 즉 **진짜 라이브러리에 대고 한 번도 실행된 적이 없었다.**

⇒ **T2(hello 배포)의 수용 기준은 "테스트 통과"가 아니라 "Cloud Run에서 실제 응답"이다.**
⇒ 그리고 **T2가 08-24 중단 기준의 판정 대상이다.** 여기서 막히면 프로젝트를 접는다.

## 3. 에이전트 구성 (의도)

```
   Agent "fleet-steward"
     model:  gemini-3.5-flash (Vertex AI)
     tools:
       ├─ list_actions()              레지스트리 조회        → 원장 없음(읽기)
       ├─ project_cost(action, params) 비용 모델 실행         → 원장 없음(계산)
       ├─ request_action(action, params)  ★ 게이트 → 실행 → 원장
       └─ read_ledger(agent, date)    일간 리포트            → 원장 없음(읽기)
```

**도구는 4개로 고정한다.** 늘리면 4분 안에 설명이 안 된다.

### 왜 `request_action` 하나만 원장을 쓰나
**부수효과가 있는 도구가 그것 하나이기 때문이다.** 조회는 지출을 만들지 않는다.

⚠️ 단, **모델 호출 자체는 별개다** — 조회만 한 대화도 토큰을 쓰고, 그것은 REQ-503에 따라
`token_meter` 항목이 된다. **도구가 공짜여도 대화는 공짜가 아니다.**

## 4. 토큰 계량 (REQ-503)

모든 모델 호출은 `ModelPort`를 통과하고, 그 포트가 **호출 1건 = 원장 1행**을 보장한다.

```
   ModelPort.invoke(prompt) ─┬─▶ 실제 Vertex 호출
                             └─▶ usage(input_tokens, output_tokens) 추출
                                    └─▶ LedgerEntry(method=token_meter,
                                                    verifiability=assumed_only)
```

**포트에서 하는 이유**: 에이전트 코드 어디서 모델을 부르든 **빠뜨릴 수 없게** 하려는 것이다.
호출부마다 기록을 시키면 언젠가 한 곳이 빠지고, 그 빠짐은 조용하다.

⚠️ **단가는 상수 모듈 한 곳에** 둔다(`pricing.py`). 모델 단가는 바뀌고, 바뀌면
`priced_at`이 낡은 것을 사후에 식별하게 해 준다.

## 5. Cloud Run 구성 (REQ-502, REQ-705)

| 설정 | 값 | 이유 |
|---|---|---|
| `min-instances` | **0** | 유휴 시 과금 0 (REQ-705) |
| `max-instances` | 2 | 폭주 방지. 데모에 2 이상 필요 없다 |
| `concurrency` | 8 | |
| `cpu` / `memory` | 1 / 512Mi | |
| `timeout` | 300s | 화해는 Job이 하므로 API는 길 필요 없다 |
| 인증 | 미인증 허용 (데모) | ⚠️ §7 |

## 6. 콜드 스타트와 데모

`min-instances=0`은 **콜드 스타트를 만든다.** 4분 영상에서 첫 요청이 몇 초 걸리면 흐름이 끊긴다.

⇒ **영상 촬영 직전에 워밍 요청을 한 번 보낸다.** 이것은 조작이 아니다 — scale-to-zero는
설계 결정이고(REQ-705), 그 대가가 콜드 스타트라는 것을 **영상에서 한 줄로 말한다.**

⚠️ `min-instances=1`로 바꿔 촬영하고 원복하는 것은 **하지 않는다.** 그러면 영상 속 시스템이
제출된 시스템과 다르다.

## 7. ⚠️ 보안 — 범위와 그 대가를 명시한다

데모 편의를 위해 **미인증 호출을 허용한다.** 이것은 다음을 뜻한다:

- URL을 아는 누구나 액션 실행을 요청할 수 있다.
- **예산 게이트가 유일한 지출 방어선이다** — 그래서 게이트가 진짜로 막아야 한다(REQ-303).

**완화**: ① 예산 한도를 낮게 설정 ② 액션 카탈로그를 **비용이 낮은 것만**으로 제한
③ 제출 후 teardown 날짜 고정(09-02).

⚠️ **이것을 "인증은 범위 밖"이라고만 적으면 안 된다.** 무엇이 대신 막고 있는지를 적어야
그 방어선이 실제로 검증된다.
