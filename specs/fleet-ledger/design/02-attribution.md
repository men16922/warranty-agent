# L4 — ★ 귀속 메커니즘

`Satisfies: REQ-203, REQ-205, REQ-206, REQ-405, REQ-503`

> **이 문서가 이 프로젝트의 핵심이다.** "에이전트의 행동에 지출을 귀속한다"는 주장이
> 실제로 성립하는지는 전부 여기에 달려 있다.

---

## 1. 문제 진술

청구서는 **리소스**에 대해 발행된다. 우리가 알고 싶은 것은 **행동**의 비용이다.
둘 사이에는 다리가 없다 — 청구 행에는 *"어느 에이전트의 어느 액션이 이걸 만들었나"*가 없다.

**다리를 우리가 놓아야 한다.** 세 가지 방법이 있고, **각각 검증 가능성이 다르다.**
그 차이를 숨기지 않는 것이 이 설계의 요지다.

## 2. 방법 ① `resource_label` — 유일하게 진짜로 검증되는 경로

### 원리
GCP 리소스 라벨은 **결제 내보내기 행에 그대로 실려 온다**(BigQuery 표준 사용량 내보내기의
`labels` 반복 필드). 그러므로 에이전트가 만든 리소스에 원장 항목 id를 라벨로 박으면,
나중에 청구 행에서 **그 id로 되찾을 수 있다.**

```
   액션 실행 ──▶ 리소스 생성 시 labels={"fl_entry": "<entry_id>"}
                          │
                          │  (GCP가 하루 지연으로 내보냄)
                          ▼
   BigQuery billing export 행:  labels[] 안에 {key:"fl_entry", value:"<entry_id>"}
                          │
                          ▼
   화해기가 label value == entry_id 로 합산 ──▶ measured
```

### 제약 — 라벨 규칙이 id 형식을 결정한다
GCP 라벨 값: **소문자 · 숫자 · `-` · `_` · 국제문자**, **≤63자**, 빈 값 허용.

⇒ `entry_id`는 **소문자 ULID 26자**로 정한다. 정렬 가능(시간 순)하고, 라벨 제약을 만족하며,
충돌 확률이 실용상 0이다. UUID(하이픈 포함 36자)도 되지만 정렬이 안 된다.

⚠️ **id 형식은 라벨 제약에서 유도된 것이다.** 나중에 id를 바꾸려면 이 제약을 먼저 확인해야
한다 — 가드 G3가 형식을 검사한다.

### 제약 — 라벨을 지원하지 않는 리소스가 있다
전부가 라벨을 받지는 않는다. 받더라도 **생성 시점에만** 받는 것도 있다.
이 경우가 REQ-206이다: **라벨 부착이 실패하면 실행을 막지 않되, 항목을 `none`으로 표시하고
사유를 적는다.**

⚠️ **여기서 조용한 성공을 만들면 안 된다.** 라벨이 안 붙었는데 `reconcilable`로 표시하면,
화해기가 영원히 못 찾고 `unreconciled`가 쌓이는데 **원인이 안 보인다.**

## 3. 방법 ② `token_meter` — 모델 호출. 행 단위로는 검증 불가

### 왜 라벨을 못 쓰나
Vertex AI 모델 호출은 **리소스를 만들지 않는다.** 청구는 SKU(모델·토큰 종류)별 집계로
들어오고, **호출 단위 식별자가 청구 행에 없다.** 라벨을 붙일 대상 자체가 없다.

### 그래서 무엇을 하나
응답의 usage 메타데이터에서 **실제 토큰 수를 읽고**, 공시 단가를 곱한다.

```python
assumed = CostFact(
    amount_usd = in_tok * price_in + out_tok * price_out,
    inputs      = {"input_tokens": in_tok, "output_tokens": out_tok},
    unit_prices = {"input_tokens": price_in, "output_tokens": price_out},
    basis       = Basis.published_rate,
)
verifiability = assumed_only          # ← 숨기지 않는다
```

⚠️ **토큰 수는 측정값이고 단가는 공시값이다. 그런데 결과는 여전히 `assumed`다** —
청구서가 이 행에 대해 말해 주는 것이 없기 때문이다. **"측정된 입력으로 계산했다"와
"청구서로 검증됐다"는 다르고, 그 구분을 지우면 이 프로젝트의 논지가 무너진다.**

### 부분적 구제 — 일간 총계 화해 (REQ-405)
행 단위로는 못 해도, **하루치 총합**은 Vertex AI SKU의 그날 청구 총액과 대조할 수 있다.

```
   token_aggregate = {
       assumed_total: Σ(그날 token_meter 항목의 assumed),
       sku_total:     그날 Vertex AI SKU 청구액 (BQ),
       ratio:         sku_total / assumed_total,
   }
```

⚠️ **집계가 맞았다고 행이 검증된 것이 아니다.** 행의 `verifiability`는 그대로
`assumed_only`다. 집계 화해는 **별도 지표**이지 행 상태를 바꾸는 사건이 아니다.
(이 구분을 흐리는 것이 가장 유혹적인 지름길이고, G3가 막는다.)

## 4. 방법 ③ `none` — 과금 리소스를 안 만든 액션

읽기 전용 조회, 판정만 하는 액션 등. **항목은 여전히 쓴다**(`amount_usd = 0`).

⚠️ 쓰는 이유: **"비용이 0인 액션"과 "장부에 없는 액션"은 다르다.** 후자는 구멍이다.

## 5. 세 방법의 비교 — 이 표가 제품의 정직성이다

| | `resource_label` | `token_meter` | `none` |
|---|---|---|---|
| 청구서로 행 단위 검증 | **가능** | 불가 | 해당 없음 |
| 즉시성 | 즉시 `assumed`, 하루 뒤 `measured` | 즉시만 | 즉시 |
| 오차를 볼 수 있나 | **볼 수 있다** | 집계로만 | — |
| `verifiability` | `reconcilable` | `assumed_only` | `assumed_only` |
| 실패 모드 | 라벨 누락 → `unreconciled` | 단가 변경을 모름 | — |

**이 표가 UI/응답에 그대로 나와야 한다**(REQ-601). 심사위원이 4분 안에 이해해야 하는 것은
"우리가 비용을 안다"가 아니라 **"우리는 무엇을 알고 무엇을 모르는지 안다"**이다.

## 6. 귀속이 실패하는 방식 (설계상 알고 있는 것)

| 실패 | 증상 | 우리의 처리 |
|---|---|---|
| 라벨을 안 붙임 | `reconcilable`인데 영원히 `pending` | 기한 후 `unreconciled` + 사유(REQ-404) |
| 한 리소스를 두 액션이 건드림 | 청구 행 하나에 라벨 값 하나 → **뒤에 쓴 쪽만** | ⚠️ **알려진 한계.** §7 |
| 리소스가 라벨 변경 후에도 이전 비용 발생 | 경계일의 귀속이 흐려짐 | 일 단위 창으로만 집계 |
| 공시 단가 변경 | `assumed`가 낡음 | `priced_at`을 남겨 사후에 식별 가능 |
| 무료 등급이 흡수 | `measured`가 0 → `ratio` 왜곡 | `delta.note`에 표시 |

## 7. ⚠️ 알려진 한계 — 숨기지 않고 문서에 박아 둔다

**공유 리소스의 귀속은 이 설계로 못 푼다.** 두 액션이 같은 리소스를 건드리면 라벨은 하나만
남고 비용은 뒤에 쓴 쪽에 전부 귀속된다.

- 범위 결정: **한 액션 = 한 리소스**인 액션만 `resource_label`로 등록한다.
  공유 리소스를 건드리는 액션은 **`none`으로 등록**하고 사유를 적는다.
- 이것을 레지스트리 적재 시점에 강제할 수는 없다(우리가 알 수 없다). **문서화된 운영 규약**이다.
- ⚠️ **이 한계를 영상에서 말한다.** 한계를 말하는 데모가 안 말하는 데모보다 강하다 —
  심사 기준의 Production Readiness는 "완벽함"이 아니라 "무엇이 안 되는지 아는가"다.
